Build plan · 16 Oct 2026 · draft for Mr. Tom

soopdoop for crews

How soopdoop becomes something a team of four developers, each running 3 to 10 agents, pays for and uses all day. It is based on the code as it is at v0.13.1, on what Claude Code 2.1.301, Codex 0.160.0 and Grok 1.0.46 can do on Mr. Tom's Mac today, and on a read of how other harness companies make money.

0. The short version

Today soopdoop shows who is online, lets one agent ask another a question through the Operator, and keeps score with XP. That is a nice layer for friends. A team pays for something else: not doing the same work twice, handing work to the agent that already knows the area, and staying in touch without sitting in Slack.

The plan adds six things, in this order:

  1. Every agent on the wire. Codex and Grok agents show up next to Claude Code agents, answer questions, and take work. Today half of a mixed team is invisible.
  2. The ledger. A crew memory of who did what, one line per finished task, built on each person's Mac. It answers "who knows about pricing and plans?" even when that person's agents are off.
  3. Heads-ups and hand-offs. When you start on something a crewmate's agent is already deep in, soopdoop says so before you start, and you can hand the task to that agent. The owner approves it, and it runs on their account.
  4. Crew notes. Live shared instructions (design rules, pricing facts, decisions) that reach every running agent on every harness at its next prompt. Nobody's agent is stuck on last month's rules.
  5. The room. The wire gets ships, props from customers, saves, shouts and a daily digest, posted to Slack. You can be heads-down and still be seen.
  6. The business. Crews as the paid unit at $10 a member a month, with the Operator as a real agent that keeps the crew's memory and writes the digest. The free tier stays for friends.

The value has to be on screen, or a team asks what this is even doing. So every surface (the HUD, the menu bar, the weekly digest) shows four numbers, and they only count things soopdoop did:

212questions answered by crewmates' agents · ~9M tokens saved
14hand-offs done by the agent that knew the area
3heads-ups acted on: duplicate or clashing work caught early
27ships this week, 9 with walkthroughs

Sample numbers. "Tokens saved" stays an estimate and never a score (AGENTS.md: no token counts on boards). The other three are counts of real events.

1. Where we are (v0.13.1)

Built and running

  • Mac app: menu bar icon, the HUD, the Operator chat, Settings. Five LaunchAgents. Self-updating releases.
  • Daemon with Claude Code hooks: presence (working / idle / waiting), one routing summary per open agent, introductions at session start, the private switch.
  • The Operator: routes a question (Opus 5.5), the owner's Mac asks a fork of the agent (Sonnet 5.5), the answer comes back. Who-questions from the summaries. The fund caps what crewmates can spend.
  • Friends, invites, knocks, flicks, XP, the board, the wire, tokens saved.
  • Sign in with Superset. Linked Superset profiles.

Missing for a team

  • Only Claude Code. Codex and Grok sessions do not exist to soopdoop. On Mr. Tom's Mac both are installed and Superset already runs their hooks.
  • No memory past the current session. When an agent closes, what it knew is gone from the crew.
  • Questions only. The Operator turns away every "do this for me".
  • No shared instructions. Every person's agents read their own CLAUDE.md at their own commit.
  • Nothing reaches Slack. Nothing about ships, customers or support.
  • No crews, only friends. No plan, no billing, no reason to pay.

One fact that shapes the plan: Mr. Tom's Superset organization has one member (himself). His crewmates are not in it. So anything that leans on Superset's org features (Remote Access, org-visible Pages, Tasks, Slack-triggered automations) does not reach the real crew today. soopdoop's own channels have to carry everything.

3. Every agent on the wire: Claude, Codex, Grok

This comes first because a team is mixed. Everything else (summaries, questions, hand-offs, the ledger) is built per harness on top of the same three pieces: a hook that tells the daemon about sessions, a transcript on disk the daemon can read, and a fork command that asks a throwaway copy of a session a question. All three exist for all three harnesses. Checked on Mr. Tom's Mac on 16 Oct 2026 (installed versions, their help text, Grok's local user guide) and against the official docs of each tool the same day; not yet run end to end.

Hook hygiene (the part that bites)

  • Cursor and Devin replay Claude's hooks, and Grok can too. Each soopdoop hook command names its harness inline (SOOPDOOP_HARNESS=codex bun hook.ts …), the way Superset's SUPERSET_HOOK_HARNESS does, and the hook drops an event when the environment says another tool is running it (CURSOR_AGENT, CURSOR_VERSION, a Claude session's CLAUDECODE around a Codex hook). A Codex run started by Claude's Bash tool is a sub-agent, not a new agent.
  • The hook forwards a few more fields to the daemon, when present: SUPERSET_TERMINAL_ID and SUPERSET_WORKSPACE_ID, Claude's CLAUDE_CODE_MESSAGING_SOCKET and its token, Grok's GROK_SESSION_ID. They stay on the machine. They are how hand-offs find the session.
  • Claude Code and Grok also take hooks of type http, which post the payload straight to a URL. Switching our Claude hooks from a bun process per event to an http hook to 127.0.0.1:47311/hook saves a process start on every tool call in every session. Worth doing in R1 while the hook files are being rewritten; Codex keeps the command form.
  • Codex hooks are keyed by the exact command text (trust). The command string must not change between releases; it already points at a fixed path (~/.soopdoop/app/apps/daemon/src/hook.ts).
  • Setup writes the Codex and Grok hook files beside Superset's, with the same backup-first rule as for Claude, and soopdoop uninstall removes only ours.

Code

  • apps/daemon/src/transcript.ts becomes transcripts/claude.ts, codex.ts, grok.ts behind one Parsed shape. Routing summaries and ledger lines come from that shape, so they look the same for every harness.
  • ask.ts grows one askArgs per harness and one result parser per harness. The fund prices by harness and model.
  • state.ts already carries harness. The HUD shows a small badge (C, X, G) per agent. AppState only gains fields.
  • Gemini CLI, Cursor CLI, Copilot CLI and Factory Droid all have hooks with session-start context; Droid has a fork command too (droid exec --fork); OpenCode has an HTTP server that can push a prompt into a running TUI. Each is one release on the R1 pattern, if the team uses it.

Done when: a Codex session and a Grok session on Mr. Tom's Mac show in a crewmate's HUD with summaries, and that crewmate's Claude agent gets a real answer from the Codex agent through ask_operator, logged in reads.log with a price.

4. The ledger: the crew's memory of who did what

Routing summaries describe agents that are running now. A team also needs the past: who built the quote page, who touched Lob pricing, who fixed email metrics last week. That is the ledger: one line per finished piece of work, per person, kept for 90 days.

16 Oct · @adalovelace · codex · vibes@quote-redesign · redesigned the quote page; new M09/M10 mocks · areas: apps/web/quote, docs/changelog · 14 files · PR #412 15 Oct · @jimmy · claude · vibes@email-metrics · fixed delivery counts double-counting bounces · areas: packages/email, apps/web/metrics · 6 files 15 Oct · @tom · claude · soopdoop@main · v0.13.1: Settings → Account box for the Superset handle · areas: apps/hud · 2 files · PR #88

How a line is made

  • On the owner's Mac, when a session ends or has been idle for 10 minutes after a turn, the daemon reads the transcript and writes the line: date, harness, workspace@branch, what was done, the areas (top-level folders of the files touched), how many files, and a PR link if the transcript shows gh pr create or gh pr merge output.
  • The "what was done" part comes from the first and last prompts and the files for free. With the owner's permission (Settings, on by default when Claude Code is installed) a Haiku call on the owner's own account writes a better one; it costs about a fifth of a cent. Codex's own ~/.codex/memories/ and Grok's summary.json title are used when present.
  • Secrets are taken out (lib/summaries.ts). Private projects never get a line. The owner sees every line in the HUD (This Mac → Ledger) before and after it goes out, and can edit or delete it. A line is at most 240 characters.
  • Nothing else leaves the Mac. The transcript stays where it is.

What it is used for

  • Who-questions with memory. "Who knows about pricing and plans?" ranks crewmates by their ledger lines (areas, words, recency) and the live summaries: "Ada: 6 pieces of work on pricing this month, last one Tuesday (lob-pricing.md, the quote page). His agent on it is off right now. Knock him?"
  • Routing when nobody is live. The Operator today says "no crewmate has an open agent". With the ledger it says who did the work and offers a knock or a hand-off for when they are back.
  • Heads-ups (§5) and the digest (§8) read it.
  • Onboarding. A new crewmate's agent can ask "what has the crew done on billing?" and get the last month in five lines.

Backend

A ledger table (hacker, at, harness, workspace, branch, did, areas[], files, pr, sessionKey), indexed by hacker and time, and by crew and time. ledger:mine, ledger:edit, ledger:forget for the owner; ledger:search for the Operator (crew only). Lines older than the plan's retention are dropped by a daily cron. The Operator's router gets the ledger's top matches as extra candidates marked "not running".

A boundary change Mr. Tom has to approve

AGENTS.md allows one thing built from transcripts to leave the Mac: the routing summary, one line per open agent. The ledger is a second thing of the same kind: one line per finished task, 240 characters, built on the owner's Mac, shown to the owner first, editable, inside the crew only. The rule "above the crew: work only, never people" still holds: a ledger line never goes up the tree. If Mr. Tom says yes, AGENTS.md and README get the new exception in the same words.

5. Heads-ups: catch duplicate work before it starts

Mr. Tom's example: he is about to start a bug ticket on wrong email-delivery metrics, and Jimmy's agent has been deep in email metrics for two hours. soopdoop should say so before he starts, not after.

How it works

  • At every prompt (UserPromptSubmit), the daemon on the owner's Mac reads the prompt from the hook payload, locally, and scores it against the crew's live summaries and the last two weeks of the ledger: shared file paths, module names and words of four letters or more (the same scoring the Operator's fake mode uses today). No model call, no network, under 5 ms. The prompt still never leaves the Mac.
  • Over the threshold, two things happen. The HUD shows a card for 10 minutes: "Jimmy's agent is on email metrics right now (packages/email, apps/web/metrics). Ask it · Hand off · Not now." And on Claude Code the agent gets a note in its context: "soopdoop: @jimmy's agent is on this area now; ask it (ask_operator @jimmy) or hand it off (hand_off @jimmy) before you build." The skill tells the agent to say it plainly to its user and offer both.
  • Codex and Grok agents get the same note at the start of their next session (the file channel) and the HUD card at once. On Grok a PostToolUse hook can add the note mid-session; that is a later refinement.
  • A heads-up counts as "acted on" when the human or the agent asks that agent, hands the task off, or knocks within 10 minutes. That is the number on the HUD. Dismissed cards are not counted and are not shown again for the same pair of agents for an hour.

The same scoring also warns about collisions: two crewmates' agents with changes in the same files right now ("Ada's agent is editing apps/web/quote/Form.tsx too"). Same card, one more line.

Done when: on two Macs, one prompt about an area the other's agent is working in shows the card and the context note within two seconds, and acting on it is counted once.

6. Hand-offs: ask a crewmate's agent to do the work

Today the Operator refuses every work order before any agent is read. That rule protected crewmates' accounts. The team wants the opposite, with consent: the crewmate agrees, and the task runs on their account, in their agent, with their context. That keeps it inside every provider's terms, because the developer runs a prompt they chose to run.

The flow

  1. Offer. From an agent (a new MCP tool, hand_off: the crewmate, the task, why them), from a heads-up card, from a crewmate's row in the HUD ("Hand off…"), or from the Operator chat ("hand this to Jimmy's email agent"). The text is shown verbatim; nothing is rewritten.
  2. Approve. The crewmate's Mac shows a card, a notification, and a badge in the menu bar: "@tom hands you: 'Fix the double-counted bounces in delivery metrics (VIB-123)' → your email-metrics agent, idle. Run now · Run when idle · Decline · Reply…" Settings per crewmate: Ask me each time (default), Run automatically when my agent is idle, Never. An offer expires after 24 hours (a scheduled function, like every interruption).
  3. Run. The daemon delivers the prompt into the chosen session by the best channel for its harness (§3): the Superset terminal, codex queue, a background copy on Claude, or the clipboard. The prompt is prefixed: "soopdoop hand-off from @tom (he approved this text, you approved running it): … When you are done, call report_back with a short summary and any PR link."
  4. Report back. The agent calls the new report_back tool (handoff id, summary, links). The hand-off is done, the wire says "Jimmy's agent did Tom's hand-off: fixed VIB-123 (PR #418)", Tom gets a notification, Jimmy gets an assist worth 20 XP. If the agent forgets, the Stop hook notices the session ended after a hand-off and the daemon asks a fork "what did you do for the hand-off?" (within the fund).

Rules for hand-offs

  • Never without the owner's consent for that crewmate, never hidden: the card shows the exact text and which session will get it.
  • Always on the owner's account. A separate allowance (default $10 a day, soopdoop fund) caps what hand-offs may cost, counted from the report-back usage where the harness reports it.
  • Logged on the owner's Mac (~/.soopdoop/logs/handoffs.log: who, which agent, when, size, cost; never the text). The backend keeps the offer text, the status and the summary, nothing else.
  • Private agents cannot be chosen. A hand-off to someone with no fitting agent becomes a knock with the text attached.

What to verify first

  • The Claude inbox socket: the message line format (the docs show the auth line, not the message shape), what a held message looks like to the owner, and that our hooks fire for the turn it starts.
  • superset terminals send from the daemon into a Claude Code terminal that Superset started, on the same Mac.
  • codex queue --thread into an interactive Codex session: does the message run at the next idle, and does the hook fire for it?
  • claude --resume ID "prompt" against a background session: that it lands as the next turn (the docs say it does from 2.1.285), and what happens when the session is not in the background.

Done when: an agent on one Mac hands a task to a crewmate's running Codex agent on another Mac, the crewmate approves it in the HUD, the task runs, report_back lands, and the wire shows it on both Macs.

7. Crew notes: shared memory that reaches every agent

A CLAUDE.md in git is the right place for a repository's rules. It is also the reason agents get stuck on old rules: it lands per repo, only after a merge and a pull, under one name for Claude and another for Codex, and it cannot say "Ada owns the quote page this week" or "the Lob prices changed on Tuesday". Crew notes are the live layer beside it.

What a note is

  • Up to 400 characters, an author, a date, optional tags (design, pricing, infra, process, people), an optional "confirm by" date, and an optional "applies when" line (a folder, a repository, a word): a note about the quote page is delivered only to sessions in that area, so the 2 KB that reaches a session is the 2 KB that matters. Devin's shared Knowledge works this way (each entry carries a trigger), and it is the one part of that product worth copying. A crew keeps at most 60 live notes.
  • Anyone in the crew writes one in the HUD. An agent can propose one with a new MCP tool, crew_note; it shows up for its owner to approve with one click before the crew sees it (a trusted crewmate's agents can post straight away, a per-crewmate setting of the leader's).
  • Age shows next to every note. At 30 days the author gets a "still true?" nudge in the HUD; an unconfirmed note stops being delivered after 45 days but stays in the history. A note can retire another ("replaces: design rules v2").

How notes reach agents

  • Claude Code: the SessionStart hook adds the live notes (at most 2 KB, newest first) under the crew introduction. When a note changes, the next prompt gets one line: "soopdoop: a crew note changed. @adalovelace (16 Oct): the quote page uses the M10 components; do not touch the old Form.tsx."
  • Codex and Grok: the daemon keeps ~/.soopdoop/crew.md fresh (crewmates' agents, notes, how to ask) and points each harness at it: a managed block in ~/.codex/AGENTS.md, and a rule file in ~/.grok/rules/soopdoop.md (loaded in every project). Changes land at the next session; a PostToolUse note on Grok can come later.
  • Any harness, any time: the MCP tool crew_notes returns all of them, and the Operator answers "what are our design rules?" from them.

The skill grows one paragraph: a note from the crew outranks the agent's memory of the same fact, and a note with a date is the current one.

Done when: Mr. Tom changes a note in the HUD, and within one prompt a Claude session on Ada's Mac and, at its next start, a Codex session on Jimmy's Mac both repeat the new rule when asked.

The scout: props from customers, on your own connectors

Support people use Claude with their own Gmail or help-desk connectors already. The scout is a small skill that runs on their Mac every hour (a LaunchAgent, like the updater): claude -p on Haiku, with the person's own Gmail or help-desk connector, looking at replies since the last run for thanks or for a turnaround, and calling the soopdoop MCP tool props with one line and no names of customers. Nothing about the email reaches soopdoop's backend but that line. It costs the person a few cents a day on their own plan, and it is off until they turn it on in Settings. Which help desk the team uses decides the first connector (§15). For a help desk with a rating event, a webhook is the cheaper second path:

A rating event names the ticket, not who shipped the fix. Tying the thanks to the person who did the work is what the ledger adds (the ticket number or the area in a ledger line), and it is something no help desk does today.

The Slack bridge

  • The crew leader pastes a Slack incoming-webhook URL into Settings → Crew (five minutes, no app review). A Slack app with chat:write can come later if threads or edits matter.
  • The digest. At a time the crew sets (default 9:00 local), the Operator writes "Yesterday in <crew>" from the wire and the ledger: ships with walkthrough links, hand-offs done, questions answered (a count), heads-ups, props and saves, notes added. Positive only. Names inside the crew are fine; the same digest above the crew describes work only. It posts to Slack, shows in the HUD under "Yesterday", and is the menu bar's first item in the morning.
  • Live mirror (off by default): ships, props and saves go to the channel as they happen.
  • Weekly: the four numbers, so the people who never open the HUD still see what soopdoop did.
  • Inbound later: a slash command (/soopdoop who knows pricing?) answered by the Operator in Slack, for the support team.

Done when: a digest with a real ship, a hand-off and a shout from the day posts to the team's Slack at the set time, and the same text is under "Yesterday" in each HUD.

9. The menu bar

10. The Operator as the crew's agent

Today the Operator is a router and a chat. For a crew it becomes an agent with a memory and a few tools, and that is the part a team pays for. It still never reads a conversation; forks answer on their owners' Macs.

What it knows

  • Live summaries (today).
  • The ledger: 90 days of who did what.
  • Crew notes.
  • The wire: a week of events.
  • The crew: handles, names, who is in focus, who shares what.

What it can do

  • Answer who- and what-questions itself.
  • Ask an agent (a relay, as today).
  • Offer a hand-off (the owner still approves).
  • Knock, with the question attached, when nobody's agent is live.
  • Write the daily digest and the weekly numbers.
  • Search the ledger and the notes for an agent's question.
  • Model: Sonnet 5.5 for routing and chat (today Opus; the routing prompt is small, and Sonnet handles it), Opus 5.5 for the digest once a day. The chat gets tool use instead of the one-shot JSON reply, so a question can be answered in two steps (search the ledger, then ask the agent).
  • The crew sees its Operator's cost for the month in Settings → Crew, as the spec asked. On the Team plan it is included; the number is still shown.
  • It speaks in the HUD chat, in agents' ask_operator answers, in the digest, and later in Slack.

12. The business

Mr. Tom's test: justify $10 a member a month by doing work that costs us something and that a "dumb connector" or the users' own agents could not do. The honest answer is that most of soopdoop's value is produced on the members' Macs, by their own agents, on their own plans. That is also the moat (nothing central reads anyone's work). What the crew pays for is the part that has to live in one place and remember: the Operator with the crew's memory, the digest, the bridge to Slack, and the hosting.

What that says

  • The seat buys the layer around the agents, never the tokens. Superset, Conductor, Zed, Warp, Linear and Letta all charge per seat for orgs, sharing, admin and SSO, and leave model usage on the user's own plan. soopdoop already works that way: forks run on the owners' plans. Keep it.
  • $10 is a real price for shared objects plus roles (Linear Basic, Raycast, Notion Plus, Zed Pro). It is below the line where buyers expect SSO and audit logs ($16 to $30 and up). A crew of eight at $10 is $80 a month, less than one Superset Pro seat times four.
  • Shared knowledge is everyone's switching cost, and nobody charges for it by name. Devin's org Knowledge, Cursor's team marketplace, Claude's managed CLAUDE.md and private marketplaces, Letta's shared agents, Entire's checkpoints. Each is one vendor, one tool. None of them is a memory of who did what. That gap is soopdoop's product (§4, §7).
  • Admin analytics is the Team hook, and it ranks people. Claude Code's dashboard has a per-user leaderboard. soopdoop's rule is the opposite (positive signals, no counts above the crew), which is a selling point to the developers who choose the tool, not the managers who buy it. The digest is how both sides see value.
  • Hosted compute is the other upsell (Conductor, Factory, Warp, Claude Managed Agents, Linear sandboxes). soopdoop's hosted work is small on purpose: the Operator's routing, the digest, drops. That is the cost base below.
  • Free with no plan to charge is not a model. T3 Code is the proof. Amp's ad-funded tier ended in March because ads "don't pay for enough frontier tokens".
  • The closest thing to a hand-off is Amp's thread sharing: tag a teammate into your thread and they can prompt your agent, on your bill. The reverse (send a task into a teammate's agent, they approve) exists only as an open proposal (relay issue #1860). Claude Code channels, Codex in Slack and Linear's delegate agents all hand work to a shared cloud agent or into one owner's own session.
  • Superset is the platform and could build the crew loop. They have org-wide terminal read and send, Pages, automations and a Slack integration. Their orgs are single-company and their standup is per person. soopdoop's answer is in the moat list below.

What nobody ships yet (searched 16 Oct 2026)

  • A memory of who is on what, from live agent work. Every expertise finder reads git blame, CODEOWNERS or documents (Sourcegraph Own, GitHub's suggested reviewers, Unblocked, Glean). Nothing answers "who is on email metrics right now" from agents. soopdoop does today; the ledger adds "last month".
  • Presence from agent work without video. Gather shows an app name inside a video office; Discord Rich Presence shows a file. Nothing quiet, nothing from what the agents are doing.
  • A hand-off into a teammate's agent that the teammate approves. Only an open issue.
  • Learnings that travel between people's agents. Claude's memory is machine-local, its Projects are single-user, Cursor's team rules are admin-typed with no API, Devin's Knowledge is hand-written. Crew notes with agent proposals and owner approval fill it.
  • Ship digests with visuals, and thanks tied to the engineer. PostHog's merged-PRs-to-Thursday-Slack-cards pipeline is the closest, and it is their internal handbook, not a product. Every help desk exposes a rating event; none links it to who shipped the fix.

Five gaps, and the plan's six things cover all five. That is the strongest reason to believe a team pays.

Where the moat is

  1. The crew's memory. The ledger and the notes are a record of who knows what, across every harness, that lives nowhere else: not in git (which has code, not people), not in Slack (which has talk, not work), not in any one vendor's memory (which is per person, per tool). Every month of use makes it worth more and harder to leave.
  2. Cross-harness, cross-org. Anthropic, OpenAI and xAI each build inside their own tool. Superset is one org at a time. A crew on soopdoop spans tools and companies by design (Mr. Tom's own crewmates are outside his Superset org today).
  3. Nothing central reads your work. Conversations stay on Macs; forks answer there; the backend holds lines and events. That is a sentence a security review can accept, and a hosted competitor that centralizes transcripts cannot say it.
  4. The social layer is sticky. XP, props, the wire and the digest make helping the rewarding thing to do, and every digest in Slack is also the pitch to the people who are not on soopdoop yet.
  5. Distribution is built in. An invite is one line; a crew is full at eight; the tree is the upsell.

Risks, plainly

  • Superset builds it. They have org-wide terminal read and send, Pages and automations; a "ask a teammate's agent" feature is one plan away. soopdoop's answers: cross-org, cross-harness, the people layer, and shipping the whole loop with Mr. Tom's crew as the proof before they do. If they do build it, the upstream path from the first plan (contribute the hooks and the friend grant) is still open.
  • A harness vendor adds team memory. It will be per vendor. Mixed teams stay ours.
  • $10 × 4 is $40 a month. One crew is not a business. The plan's bet is that the digest and the invite line bring the next crew. The tree and the Company tier are where the price grows.
  • Hand-offs can feel like surveillance or hijacking. Consent per crewmate, exact text, owner's account, the allowance, and the log are not optional.
  • Hooks and flags change under us. Codex and Grok ship weekly. Every release re-runs the three forks on real sessions before it ships (the release script can do it on the releasing Mac).
  • The name. Still needs the check with Superset.

13. Build order

Ten releases, each cut with bun run release and installed on the crew's Macs within six hours, each ending with something the team uses the next morning. The order puts the things that make value visible first and keeps every release compatible with the one before (RELEASING.md: add, never rename or remove in the same release). At the pace of the last three weeks (103 commits in five working days), a release is two to four days of work.

14. Rules that do not bend

  • A conversation never leaves the Mac. Three one-line things built from it do, each made on the owner's Mac, shown to the owner, editable by the owner, and kept inside the crew: the routing summary (one per open agent), the ledger line (one per finished task), and the answer a fork writes to one question. Prompts are read locally for heads-ups and go nowhere.
  • Nothing runs on your account without your say. A hand-off runs only with consent for that crewmate, shows its exact text first, runs on your plan, and is logged on your Mac. The fund and the hand-off allowance are checked on your Mac, so neither a crewmate nor the backend can get around them.
  • Agents never talk to each other directly. Every question and every hand-off goes through the Operator, and the Operator never reads a conversation.
  • Private agents never leave the machine. No summary, no ledger line, no heads-up, no hand-off.
  • Every interruption expires by a scheduled function: knocks 30 s, heads-up cards 10 min, hand-off offers 24 h, shouts 24 h.
  • Above the crew: work only. No names, no counts, no ledger lines. The digest that leaves the crew describes work.
  • No token counts on boards. Tokens saved stays one estimate per person and per crew.
  • Positive signals only. The wire and the digest carry ships, assists, props, saves and notes. Never "idle since", never "fewest", never a ranking by output.
  • Nothing from Superset's code. Hooks, the CLI, Pages and Remote Access only. superset terminals send is the CLI.

15. Decisions for Mr. Tom

  1. The ledger as a new boundary exception. One 240-character line per finished task leaves the Mac, inside the crew, owner-editable (§4). Yes or no decides R3, R4 and the who-questions.
  2. Hand-off default. This plan picks "ask me each time" per crewmate, with "run automatically when idle" as an opt-in. The other way round makes hand-offs faster and riskier.
  3. Which help desk first for the scout: Gmail only, Help Scout, Intercom, Front or Zendesk. The connector decides a week of R8.
  4. Slack: webhook now, app later? A webhook posts in five minutes with no review. Threads, edits and the slash command need an app.
  5. Price and tiers as in §12: Free for friends, Team at $10 a member a month, Company later. Yearly at ten months.
  6. Drops hosting on the soopdoop.com Cloudflare account (R9), or links only until a crew asks.
  7. The name. "soopdoop" contains Superset's mark. Selling needs the check with them that the first plan already asked for.
  8. Model for the Operator. Sonnet 5.5 for routing and chat (cheaper, enough) and Opus 5.5 for the digest, or Opus throughout as today.

What this plan did not check: no Codex or Grok fork, queue or hook was run; the flags come from the installed help text, Grok's local user guide and the official docs read on 16 Oct 2026. The Claude inbox socket, claude --resume ID "prompt" into a background session and superset terminals send from the daemon were not run. Prices and features of other products are from their public pages the same day (§12) and can change.
