Build plan · 28 Sep 2026 · draft for Mr. Tom

soopdoop

A multiplayer layer on top of Superset. This plan is based on reading Superset's source (github.com/superset-sh/superset, commit ee5233e, 28 Sep 2026), not on the docs site, which is blocked from this machine.

What Superset does not have (this is the product)

  • Friends and crews across organizations. Superset's teams are inside one org and are "not an access-control mechanism". Host grants are per org.
  • Knocks and eyes. No expiring attention requests. Notifications are "your agent finished".
  • The Operator. Nothing reads another person's agent context and answers a question. Agents never talk to each other at all.
  • The tree. No structure above a team, no cross-crew routing, no heads-ups (collisions, duplicate work).
  • Play. The leaderboard is tokens and cost. There is no assist, props, XP, or crew goal.
  • Company tracker. The leaderboard is per person. Nothing sums by company and shows only companies.

2. The licence sets the shape

Elastic License 2.0

We may copy, modify and distribute Superset. We may not "provide the software to third parties as a hosted or managed service" that gives access to a substantial set of its features. So:

  • Our backend must be our own code. It may call Superset's API on the hacker's behalf. It may not be a hosted copy of Superset's API.
  • A modified desktop app is allowed if we mark it as modified and keep the licence notices. It must not remove licence-key features (Pro).
  • Everything we push into a hacker's machine (daemon, hooks, plugin, skill) is our code, running next to Superset. No licence problem.

3. Decision: how the layer attaches to Superset

A · Fork the desktop app

Add the rail inside Superset's window. Full control of the UI. Cost: we own a 10,000-file Electron monorepo that moves ~70 commits a day. Every rebase is ours. Users must install our build instead of Superset's.

B · Companion (recommended)

Our own daemon, backend, plugin and rail. The rail is a small always-on-top window beside Superset (Electron or Tauri), and the same UI also opens as a Superset Page inside a workspace pane. Jack in deep-links into the user's real Superset. Zero fork. Ships against any Superset version.

C · Upstream only

Contribute crews, knocks and the Operator to Superset itself. Right long-term home for presence and knocks, wrong for a product we want to own and for cross-org crews. Do this later, for the hooks we need.

Recommendation: B now, with two upstream PRs later (a documented local event feed from the host service, and a "friend host" grant that crosses orgs). B is the only option that does not put a fork between us and every Superset release.

Components

ComponentWhat it isWhy this way
subset daemon
Bun, one binary		Runs on each hacker's machine. Installs our lifecycle hooks into the harnesses Superset supports (Claude Code first). Hooks give session start, prompt submit, turn stop, session end, and the transcript path. Keeps presence: which agents, which workspace, working / idle. Serves transcript reads to the Operator on request (never streams them). Sums tokens by model from local session logs once an hour.Hooks are a public harness contract; the Superset host-service tRPC is internal and may change. The daemon works even when Superset is closed, and needs no Superset fork.
backend
Convex		Hackers, friends, crews (cap 8), tree nodes, presence, knocks (30 s) and eyes (5 min) with scheduled expiry, the relay log, assists, props, XP, badges, boards, company tracker, focus mode and ping settings.Presence, subscriptions and scheduled functions are Convex's strengths. The team already runs Convex in production. Our own code, so ELv2 is not a concern.
Operator service
Node worker + Claude API		One coordinator per crew (and per tree node). Keeps a short routing summary per agent, updated from turn-stop events. On a question: picks the agent, asks that hacker's daemon for a bounded slice of the transcript (last N turns + files touched), answers in one line, logs the relay, drops the context.The spec's "reads, shortens, forgets" is a stateless call with a summary index. Prompt caching keeps a 40k-token read cheap.
plugin
Superset plugin: skill + MCP		A SKILL.md that teaches any agent when to ask the Operator, and an MCP server with ask_operator, knock, request_eyes, crew_status. Installed through Superset's plugin catalog or npx skills add.This is how Superset wants third-party agent tooling delivered. Works for all 20 harnesses at once.
rail
web UI; Electron shell		The prototype we already have, wired to Convex. Ships two ways: a slim always-on-top window docked beside Superset, and the same page published as a Superset Page so it can live in a workspace pane.No fork, and the rail can be inside the Superset window on day one via Pages.
jack inWatch / comment / co-drive = Superset Remote Access. Our backend calls the Superset API (with the owner's key) to grant the visitor host access for that session, then deep-links the visitor into that workspace. Co-drive prompts go through Superset's own terminal send, labelled with the visitor's handle.Superset already streams remote terminals and enforces host membership. We add the request, the approval, the label and the timer.

5. Phases

Each phase ends with something a hacker can use. Order follows the spec's build order, adjusted for what Superset already provides.

Phase 03 days

Decide, spike, scaffold

  • New repository soopdoop (not inside vibes). Bun workspace: apps/rail, apps/daemon, packages/convex, packages/operator, packages/plugin.
  • Spike 1: our hooks in Claude Code report start / stop / transcript path while Superset's own hooks keep working (both can coexist; Superset's hooks are no-ops outside its terminals, ours are not).
  • Spike 2: a Superset Page can host our rail and stay live (WebSocket to Convex from inside the Page pane).
  • Spike 3: the Superset API can grant host access programmatically (the MCP has hosts_list and organization_members_list; host member grants may be desktop-only today). If not, jack in v1 is "open Superset → Settings → Hosts" with our button beside it.
  • Move the spec and prototype into the repo as docs/spec.md and apps/rail/prototype.
Phase 12 weeks

The knock (vertical slice)

  • Sign in with Superset (OAuth via api.superset.sh) → hacker + handle.
  • Daemon: presence from hooks → Convex. Rail shows friends with LEDs and agent counts, with the "show only what I allow" settings.
  • Knock with a link or a Superset Page; 30 s expiry by scheduled function; "not now" / "they're looking". One open knock per pair.
  • Friends by handle and by invite link. Focus mode.
  • Rail as a docked window and as a Superset Page.

Done when two people on two machines see each other's LEDs change within 2 s of an agent starting, and a knock expires on its own.

Phase 23 weeks

Crews and the Operator

  • Crews of 8 inside one Superset org. Crew leader = first inviter. Shared set view: every member's agents.
  • Daemon: on each turn stop, send the Operator a routing summary delta (agent, workspace, files touched, one line). The owner can see and edit it.
  • Operator service: ask → route → availability (idle: read now; working: read last finished turn, or wait if the question is about the change in flight; ∅: say so) → bounded transcript read via the daemon → one-line answer → relay log with the two token numbers → "+1 assist".
  • Plugin: ask_operator MCP tool and the skill that tells an agent to try the Operator before a codebase search.
  • Cost sharing: even split across active members, monthly cap, leader can pay all.

Done when an agent in one workspace gets a correct one-line answer from a crewmate's agent context without either human touching anything, and the relay appears in both hackers' logs.

Phase 32 weeks

Eyes and jack in

  • Second set of eyes: 5-minute banner, one "later", join opens the sender's workspace in Superset.
  • Jack in levels. Watch and comment use Superset Remote Access plus a host grant scoped to the session; co-drive needs the owner's approval each session and sends prompts through Superset's terminal API with the visitor's handle prepended. Purple border while anyone co-drives.
  • Drops = a Superset Page pinned to the crew shelf.
Phase 42 weeks

Play

  • XP (assist > eyes > ship > props > ask), ranks n00b → legend, the eight badges, the wire, props on ships.
  • Ships from GitHub (merged PRs, non-generated files) through Superset's GitHub connection or the hacker's own token.
  • Boards inside a crew: assists, eyes, ships, props. No token board.
Phase 53 weeks

The tree and the tracker

  • DUPER nodes: pair crews (suggested from overlapping repos, confirmed by leaders), one Operator per node holding two child summaries (work only, no people), relay up and down, heads-ups for collisions and duplicates, crew-only topics.
  • "Where companies are built": daemon token rollups by model → company sums. Companies opt in. Expand a company to see models. No crews, no people.

6. Risks and open questions

  • Cross-org jack in. Superset host grants are inside one org. Friends in different companies get presence, knocks and the Operator in v1, but not jack in, until an upstream change or a relay of our own.
  • Transcript privacy. The daemon only ever sends a transcript slice to the Operator for an agent the owner marked open, and only for the duration of one answer. Private agents never leave the machine. This must be visible in the UI and in the logs from day one.
  • Operator cost. A read of a 40k-token transcript per question. Prompt caching and a per-crew monthly cap keep it bounded; the tracker shows every hacker their share.
  • Superset changes fast. We depend only on public surfaces: harness hooks, the MCP/SDK, Pages, Remote Access. The SDK is marked alpha. The daemon must never import Superset internals.
  • Token rollups are self-reported by the daemon. Same as Superset's own leaderboard. The tracker labels itself "reported by members".
  • Name. "soopdoop" contains Superset's trademark. Check with them before launch; the product name may need to change (the tree names DUPER and SUPERDUPERDUPERSET are internal).

7. First build, this session

If the plan is approved, the first thing built is the Phase 1 slice, in this order:

  1. Scaffold the repo and the Convex schema for hackers, friendships, subsets, knocks.
  2. The daemon with Claude Code hooks → presence in Convex (one machine first).
  3. The rail (from the prototype) reading live presence and sending a knock, with scheduled expiry.
  4. Sign-in with Superset and handles.

Spikes 1–3 run in parallel with step 1; their results can change Phase 3 but not Phase 1.
